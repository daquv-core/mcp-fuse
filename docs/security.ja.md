# Security model

[English](security.md) | [한국어](security.ko.md) | **日本語**

mcp-fuse はエージェントとデータを持つシステムの間にあるため、ツールをどう扱うかよりも、認証情報と本文をどう扱うかの
ほうが重要です。このページは、何を保証するか、なぜか、何を利用者に任せるかをまとめます。脆弱性を報告するには
[SECURITY.md](../SECURITY.md) を参照してください。

## 保証すること

**トークンを他へ渡しません。** エージェントが提示したトークンは mcp-fuse 向けのものです。introspect し、
mcp-fuse の `resource` が audience に含まれている必要があり、呼び出し元が誰かを知るためにだけ使います。backend が
受け取るのは、その backend 自身の認可サーバーが、その人のために、その backend を audience として発行したトークン
だけです。呼び出し元のトークンを転送すると、backend が自分宛てでないトークンを受け入れたり、あるサービス用の
トークンを持つ攻撃者が別のサービスで再利用したりできてしまいます。MCP 認可仕様が禁じる confused deputy 問題
（「トークンパススルー」）です。

**backend へは MCP クライアントが送るものだけを送り、呼び出し元が選んだものは送りません。** `Content-Type`、
`Accept`、`User-Agent`、`MCP-Protocol-Version`、backend 自身の `Mcp-Session-Id`、自身の `Authorization`、そして backend の
ログを私たちのログと突き合わせられるようにする `X-Request-Id` です。呼び出し元のヘッダーはコピーせず、
`X-Forwarded-*` も追加しません。呼び出し元が送ったリクエスト ID は、明らかに ID である場合（`[A-Za-z0-9._-]`、最大
64 文字）にだけ渡します。

**ツール呼び出しはそのまま通過します。** 引数と応答は JSON-RPC のフレーム以上には解析せず、再エンコードせず、
保存しません。エージェントが送ったものがバイト単位でそのまま backend に届き、逆方向も同じです。

**機密になりうるものは記録しません。** ログに残るのはツール名、backend、遅延、ステータス、リクエスト ID です。
リクエストや応答の本文、トークン、シークレット、backend や認可サーバーが返したエラーの文面は残りません（分類や
コードだけです）。

**ある人の接続が他の人のものになることはありません。** grant のキーは introspection が確定した人です。ルーティングの
索引も人ごとです。backend の接続には 2 つの証明が必要です。

- *誰が接続しているか。* 人がエージェントがログインする認可サーバーでサインインし、リンクが作られた本人で
  なければなりません。接続リンクは署名付きで 10 分間有効な ticket で、ID ではなく主張です。この手順がないと、
  リンクを渡された人が自分自身として backend にサインインし、そのトークンがリンクの持ち主のものとして保存され、
  リンクの持ち主がその人として動けてしまいます。
- *どのブラウザーか。* リンクを開くときに設定される cookie（`HttpOnly`、`SameSite=Lax`、接続ページに限定）がすべての
  手順で戻ってくる必要があり、すべての `state` の値は 1 回しか使えません。これがないと、backend のサインイン用
  アドレスを他の人に渡せてしまい、その人のトークンが最初の人のものとして保存されます。

**grant は保存時に暗号化されます。** `state_file` は `secret_file` から導出した鍵を使う AES-256-GCM で、`0600` で
作成され、一時ファイルを経由して書き込まれるため、途中でクラッシュしても以前の状態が残ります。接続 ticket は、同じ
シークレットから導出した別の鍵で署名されます。

**認可サーバーは信頼に値する必要があります。** mcp-fuse は、PKCE S256 を示さないサーバー、メタデータが別の issuer
を名乗るサーバー、保護リソースメタデータが別の resource を名乗るサーバーを拒否します。認可レスポンスの `iss`
パラメーター（[RFC 9207](https://www.rfc-editor.org/rfc/rfc9207)）も確認します。

## 利用者に任せること

- **ホスト。** `state_file` と `secret_file` を読める人は、保存されたトークンを使えます。この 2 つのファイルとサービス
  ユーザーを保護してください。バックアップも同じ注意で扱ってください。state ファイルには有効な認証情報が入って
  います。
- **backend への TLS** はシステムの信頼ルートを使います。プライベート CA を使う backend では、その CA がシステムの
  信頼ストア（またはコンテナイメージ）に必要です。
- **リバースプロキシ。** mcp-fuse は既定で loopback にバインドし、前段で TLS が終端されることを前提とします。
  `listen` を直接公開しないでください。
- **backend が返すもの。** mcp-fuse は結果を検査しません。結果でデータを漏らす backend は、mcp-fuse を通しても
  漏らします。マスキングと認可は backend の役割です。
- **認可サーバーの可用性。** introspection に到達できない場合、呼び出し元は `503` を受け取ります（`401` ではありません。
  `401` ではクライアントが再ログインに向かいます）。成功した introspection は最大 60 秒、またはトークンの `exp`
  までキャッシュされるため、認可サーバーで失効させたトークンがその間は動作する可能性があります。
- **インスタンスは 1 つ。** grant はローカルのファイルに、進行中の接続はメモリにあります。インスタンスが 2 つあると
  分かれてしまいます。

## 意図的にしないこと

ポリシー、マスキング、結果の加工、結果のキャッシュ、失われたセッションを開き直すことやトークンの更新を超える
リトライ、そしてあらゆる LLM。これらは backend の役割です。[CONTRIBUTING](../CONTRIBUTING.md) を参照してください。
